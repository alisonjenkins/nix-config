# Implementation Plan: Foveated rendering for VR games that lack it

**Branch**: `spec/005-vr-foveated-rendering-injector` | **Date**: 2026-10-05 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/005-vr-foveated-rendering-injector/spec.md`

## Summary

Add per-game fixed-centre foveation to D3D11 VR games under Proton by patching DXVK to apply
Vulkan fragment shading rates, measure the effect with GPU timestamp queries and a power
sampler, and keep a go/no-go verdict per game. The patch lives in a fork of DXVK consumed as
a flake input, is delivered as a Steam compat tool that stays inert unless a launch option
sets `DXVK_FOVEATION`, and is configured through DXVK's own per-game config file generated by a
home-manager module. A Vulkan layer for Vulkan-native games and a real gaze source are later
phases that reuse the same core. Research and decisions are in [research.md](research.md).

The plan starts with five short spikes, because five facts that the design depends on are
unverified: the layered-target rate image, the game's eye-image size, the compat-tool
layering, headless VR, and the DXVK base version.

## Technical Context

**Language/Version**: C++ for the DXVK fork (its own toolchain, Meson). Python 3 for the
measurement sampler and report (standard library only). Nix for packaging.

**Primary Dependencies**: DXVK (fork of `doitsujin/dxvk`), Vulkan 1.3 with
`VK_KHR_fragment_shading_rate` and `VK_KHR_dynamic_rendering`, Proton (the user's runner) for the
compat tool, MangoHud as a cross-check only.

**Storage**: files. A DXVK config file per game (generated), measurement logs and a verdicts
file under `docs/vr-foveation/` (records of games tried).

**Testing**: unit tests for profile parsing and pass recognition, written as plain C++ tests
that run in the fork package's check phase without a GPU; Python tests for the report
statistics and the home module's generated config, exposed as flake checks so `just check`
runs them on a machine with no headset or game (SC-007); the shading-rate probe (`research/vrs-probe/run.sh`) for GPU behaviour, run by hand
on the target GPU because the Nix sandbox has no GPU; per-game runs for the verdicts.

**Target Platform**: NixOS on ali-desktop (RX 9070 XT, Mesa 26.x), Steam with Proton, headset
through SteamVR or Steam Link.

**Project Type**: a fork of a third-party library plus packaging and docs in this repository.

**Performance Goals**: any GPU frame time or power reduction beyond measured noise on at least
one heavy D3D11 VR game (SC-001). No minimum percentage. With foveation off, no change beyond
noise (SC-005).

**Constraints**: must be inert unless opted in; fall back to normal rendering on any detection
or driver failure; coarsest rate 2x2 and 8x8 tiles on this GPU; one shared rate image across
layers; limited to verified GPU and driver combinations (FR-017); no game files modified.

**Scale/Scope**: about 100 owned VR titles, a handful of heavy D3D11 games in scope, one
verified GPU.

`flake-modules/packages.nix` so PR checks build them.

## Phases and order

Rule for every phase that changes the fork: fork changes land as fork commits with their tests
first, then this repository updates the `dxvk-foveation` input to the fork commit and rebuilds
`.#proton-foveated` (constitution VII). Each such phase has an explicit task for that step.

### Phase 0: Spikes (each answers one unverified fact; none ships code)

| Spike | Question | Done when |
|-------|----------|-----------|
| S1 | Does a one-layer rate image work on a 2-layer render target without a view mask, on this GPU? | The probe gains a case for it and results are recorded; if it fails, layered passes use per-draw rates and the plan notes it. |
| S2 | What does Fallout 4 VR render (API, target size, layers, format, samples)? Does DXVK's per-exe config work as the profile carrier? | Fallout 4 VR started once from the library, its API confirmed in the logs, large targets listed from DXVK's log output, and the config mechanism shown to select per game. |
| S3 | Can a separate compat tool directory, made from the user's DW-Proton release with only its DXVK replaced (pinned derivation, or a copy of the current runner), survive the runner updater? | A game launches with the tool and uses the replaced DXVK, confirmed by DXVK's version line in its log, and one build route is chosen. |
| S4 | Does Fallout 4 VR keep rendering on SteamVR's null driver? If not, can the Quest through Steam Link give a fixed pose? | One repeatable 60-second run produces frame timing, or the fallback is chosen and recorded. |
| S5 | Which DXVK base does the user's Proton runner ship, and can the patch rebase onto it? | The base version chosen and a clean build of the unmodified fork in Nix. |

Spikes S2 to S4 launch a game, which the owner starts or approves.

### Phase 1: Measurement harness (Story 1)

1. Failing tests for the statistics rule (median, noise, "gain beyond noise") in the Python
   package, then implement.
2. Sampler for discrete-GPU power and clocks, selected by PCI device, with energy integration.
3. Timestamp-query measurement in the fork behind `DXVK_FOVEATION_MEASURE`, logging per-frame
   total and eye-pass GPU time.
4. Baseline reports for Fallout 4 VR with foveation off, including the noise level: once with
   stock Proton and once with the patched tool and the option unset, so that SC-005 (no change
   when off) is measured and not only argued.

### Phase 2: Fixed-centre foveation and fallbacks (Stories 2 and 3)

1. Failing tests for profile parsing, pass recognition, rate-map generation (including a
   check of the generated rate codes against the probe's recorded values, and regeneration
   when the target size changes), and every fallback path (no profile, no match, unverified
   GPU, 8x MSAA, extension missing).
2. Enable the extension and feature only when foveation is on; dynamic state; creation flag;
   rate image; set-rate per matched pass.
3. Per-game opt-in through `DXVK_FOVEATION`; off path unchanged.
4. First on/off comparison on Fallout 4 VR, recorded with artefact screenshots.

### Phase 3: Profiles, discovery and verdicts (Story 4)

Discovery mode, the home module generating the DXVK config, the verdicts file, and the topic
doc and ADR. The topic doc covers the single-launch tuning path, the eye-placement consequence
of the shared rate map, known overlay conflicts (frame generation, upscalers), the
anti-cheat warning and the screenshot procedure for SC-002.

### Phase 4: Gaze interface (Story 6, interface only)

The sample format and source interface in `contracts/interfaces.md`, plus a synthetic source
tested with a known path and a timeout back to the fixed centre.

### Phase 5: Vulkan-native and D3D12 (Story 5), later

A Vulkan implicit layer reusing the profile and rate-map code, started only after Phase 2 has
a go verdict on at least one game.

## Risks and mitigations

| Risk | Mitigation |
|------|------------|
| Layered rate image unsupported for DXVK's stereo case | Spike S1 first; fallback to per-draw rates. |
| Eye-image pass cannot be told apart in a game | Discovery mode and per-game profile; a game that cannot be recognised gets a no-go verdict, not a heuristic that guesses. |
| Headless VR does not render on Linux | Spike S4; fall back to the Quest with a fixed pose and exclude stream-encoder load from the comparison. |
| DXVK upstream moves faster than the runner's bundled version | Keep the patch confined to two new files and small hooks; pin the fork to a tag; rebase on the base chosen in S5. |
| The runner updater overwrites the compat tool | Separate directory the updater does not manage; confirmed in S3. |
| Gains are within noise for the heavy games | Allowed outcome: a no-go verdict is recorded and is a valid result (SC-003). |
| Visible artefacts from 2x2 periphery | Artefact screenshots in every verdict; region size and rate bands are profile settings. |
| Another driver treats the missing creation flag as an error | FR-017: disabled on unverified GPU and driver combinations. |
