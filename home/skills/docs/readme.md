# README

## What a README is for

A README answers four questions for a stranger: what does this do, why would I use it, how do I start, and where do I get help. It is the entry point and router, not the manual. GitHub Docs notes it contains "only information necessary for developers to get started using and contributing". GitHub truncates rendering past 500 KiB.

## First screen

Ensure these items are visible without scrolling:
- Name of the project.
- Pitch under 120 characters on its own line, matching the package or repo description if present.
- Status line when not active and usable (deprecated, experimental, not accepting contributions).
- Minimal runnable example or single install command.

Evidence note: in a study of 393 GitHub READMEs (Prana et al., 2018), "how" content appears in 88.5% of files, but "why" appears in only 25.7% and status ("when") in 21.4%. The why and status lines are what most READMEs lack.

## Section order

```text
Title
Pitch (one line)
Status (only if not active)
Demo (screenshot or terminal capture, optional)
Quickstart (minimal example first, then the one install command, copy-pasteable)
Install (every platform and option, if more than one)
Usage
Documentation (links to tutorial, how-to, reference, explanation)
Support (where to ask, where to file bugs)
Contributing (3 lines plus link to CONTRIBUTING)
License (name or SPDX id, last)
```

Omit any section that does not apply. A short README is the default. See readme-visuals.md.

## Linking to other docs

Put a Documentation section after Usage and before License (it is already in the template above). Use one descriptive line per link, relative links, in a list or small table.

Link text describes the target ("Configuration reference"), never "click here" or "here" or a bare URL.

Do not duplicate: the README states the one-line summary, the linked page owns the detail.

Use relative links for files in the same repo so they work on every branch and fork; GitHub resolves them. Exception: crates.io resolves relative README links against the repository field when it is on github.com, gitlab.com or bitbucket.org; npm and PyPI docs and source show no such handling, so use absolute URLs for a README published there.

Every page under docs/ is reachable from the README: either directly or through a docs/README.md index that lists every page with one line each. The index rule is local policy (observed in the exemplars checked, no source states it).

Link CONTRIBUTING.md, SECURITY.md and CHANGELOG.md explicitly; GitHub also surfaces some of them in its own UI, but a registry page does not.

Heading anchors: GitHub generates them by lowercasing, replacing spaces with hyphens and dropping punctuation; renaming a heading breaks inbound links, so check fragment links in CI. lychee with --include-fragments checks them, and markdownlint rule MD051 flags invalid fragments.

Monorepo: link the single package index from the root README (see repo-shapes.md). Repo layout: see structure.md.

## Decisions where the sources disagree

| Question | What sources say | Rule here |
|---|---|---|
| Length | makeareadme: too long beats too short. GitHub and Art of README: as short as possible | Short, move depth to linked docs rather than cutting it |
| Install or usage first | standard-readme: install first. Art of README: usage first so readers can judge fit | Pitch, then a minimal example, then install |
| Badges | standard-readme: optional. Art of README: warns against heavy use | At most 3 to 5, only ones that report a real property such as CI status, version, license. Never decorative |
| Table of contents | standard-readme: requires one over 100 lines. GitHub: generates one from headings | Skip it, GitHub renders an outline |

## By repo type

| Type | Add or emphasise | Evidence |
|---|---|---|
| Library | Minimal usage example, install per package manager, link API reference | Guide-level |
| CLI tool | Install matrix with one subsection per platform, example commands first, link to full help or man page. Ripgrep, fd and bat READMEs are models | Guide-level plus exemplars |
| Application | How to run locally, config, screenshot | No specific source, general guidance applied |
| Infrastructure or IaC module | Requirements, minimal usage, input and output tables generated by tooling such as terraform-docs if present, link to full examples | Convention from blog posts, not studies |
| Dotfiles or system config | What each file does, how to apply and how to test, state that no secrets live in the repo | Convention, weak sources |
| Monorepo | Root README is purpose, setup and an index of packages. Each package README is short. Shared text lives in one place | Convention, weak sources |

The nixpkgs README is a pure map to its manuals, a valid pattern for a very large repo.

## README versus AGENTS.md and CLAUDE.md

A README is for humans (quick start, description, contribution guidelines). AGENTS.md or CLAUDE.md hold what a coding agent needs every session: build and test commands, code style, layout, rules. Do not duplicate between them; link instead.

Claude Code reads AGENTS.md only when no CLAUDE.md exists in the working directory or above it. With both present it reads CLAUDE.md alone, unless CLAUDE.md imports AGENTS.md. Keep one source of truth and import it from the other file. Keep each agent file under about 200 lines with concrete verifiable rules. No source says to write READMEs for machines. The useful middle is stable headings and fenced code blocks with a language tag, which help both readers (inference). See agent-files.md for the single-source-of-truth rules.

## Keep it accurate

- Run README snippets as tests where the language supports it (Rust: include the README as crate docs so doctests run; Python: mdoctest or pytest-codeblocks if present).
- Run markdownlint for structure if present (rules MD040 fenced blocks need a language, MD034 bare URLs, MD059 descriptive link text, MD045 image alt text).
- Run Vale for prose style if the repo already uses it.
- Run lychee for dead links on a schedule if present.
- Update the README in the same change that alters a command or flag.

## Anti-patterns

| Pattern | Fix |
|---|---|
| Install steps buried under background prose | Quickstart in the first screen |
| Wall of badges | Cap at 3 to 5 meaningful ones |
| Pitch below badges or a table of contents | Pitch first |
| Quickstart that assumes prior setup or a hidden API key | List prerequisites, test on a clean machine |
| "Click here" link text | Descriptive link text |
| Stale TODO or roadmap sections | Delete or link to the issue tracker |
| Marketing language | State what it does, with a number or an example |
| Duplicating reference docs that drift | Link or generate |
| Text inside screenshots | Text in the page, image only for visuals |

## Before handing a README over

- [ ] Pitch line present and under 120 characters
- [ ] Why and status stated
- [ ] Quickstart commands were run, or the README says untested
- [ ] Every section present is needed
- [ ] License named
- [ ] Links resolve
- [ ] Prose passed the `writing` self-audit
