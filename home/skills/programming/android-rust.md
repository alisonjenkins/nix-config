
# Android apps in Rust

Read when building, packaging, signing, debugging or testing an Android
app written in Rust with no Java or Kotlin source: APK, dex, `d8`, `aapt2`,
`apksigner`, JNI `Java_` exports, `UnsatisfiedLinkError`, dx/Dioxus
Android, Android Auto, the DHU. Rust language rules stay in
[languages/rust.md](languages/rust.md).

Worked example: Pharos (phone, TV, Android Auto media), a Rust
repo with no Java or Kotlin source. Paths below are relative to that repo.

## Why Java classes are unavoidable

Android starts every component by instantiating a Java class named in the
manifest, loaded from the app's dex.

- Components: `Activity`, `Service`, `ContentProvider`, `BroadcastReceiver`.
- Rust cannot be one of them. Only `NativeActivity` is native, and only for
  activities.
- A dex loaded at runtime cannot be named in the manifest: the platform
  loads the component before app code runs.
- `java.lang.reflect.Proxy` implements interfaces only. It cannot subclass.

So generate thin classes that extend the framework class and forward every
call to a `native` method. Rust implements those through JNI. Pharos
records this in ADR-0127.

## Pipeline

1. Build the Rust cdylib for `aarch64-linux-android` (`libmain.so` with dx).
2. Emit `.class` files from Rust (`crates/pharos-classgen/`).
3. `d8` turns them into a dex.
4. Add the dex and the library to the APK, resources from `aapt2` or gradle.
5. `zipalign`, then `apksigner sign`.
6. Check the APK, install with `adb -s <serial> install -r`.

## Core rules

- Use framework classes (`android.service.media.MediaBrowserService`,
  `android.media.session.MediaSession`), not AndroidX or Media3. The APK then
  needs no Java libraries.
- Every JNI signature is a string checked only at run time. Test the
  generated classes on a desktop JVM first ([jvm-check.md](android-rust/jvm-check.md)).
- A `Java_` export the linker drops compiles fine and throws
  `UnsatisfiedLinkError` on the device. Keep exports alive and check
  them with `llvm-nm`.
- Native threads you attach from Rust find classes through the system
  loader, which does not see the app's. Look app classes up on the thread
  the framework called, cache them as global refs.
- Do not hardcode tool paths. Probe with `command -v`. A Nix dev shell
  with the Android SDK, NDK and build-tools is one option; `$ANDROID_HOME`
  is the usual anchor.
- Always `adb -s <serial>`. Never kill or restart an adb server you share.
- Log ids, never titles. Log every JNI entry so one logcat line proves a hop
  reached Rust.
- Bump `versionCode` every build (minutes since an epoch) so each install
  counts as an upgrade.

## Facts worth knowing

- Tooling used: build-tools 35.0.0, platform `android-34` `android.jar`,
  `--min-api 26`.
- Phones are arm64. A 32-bit-only phone was not a target.
- Android Auto never shows the app's UI. It binds the media browser
  service and draws its own lists.
